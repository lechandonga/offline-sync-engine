# offline-sync-engine

本地优先（local-first）的多副本数据同步引擎，支持离线编辑、增量同步、
确定性冲突收敛、快照压缩、版本互通与崩溃恢复。

## 快速开始

```go
e, _ := sync.Open("/data/replica-a", "A")
e.Set("key", json.RawMessage(`"value"`))
e.Delete("old-key")

// 与另一副本双向增量同步（幂等，可安全重试）
sync.SyncPair(engineA, engineB)

// 压缩历史变更，控制存储与同步成本
e.Snapshot()
```

## 收敛语义

- 每个副本的本地变更先**追加到持久化日志**（fsync）再应用到内存状态，
  离线期间的所有修改都被确认保存。
- 副本间通过**版本向量**（replica → 已见最大连续序号）交换增量：
  只传输对方缺失的变更，开销随新增变更量线性增长。
- 接收端按**变更 ID 幂等去重**，因此重复投递、乱序到达、中途断连
  都不会造成重复应用或状态分叉；断连后重新执行同步即可继续完成。
- 所有副本应用同一变更集合后必然收敛到**相同状态**：
  物化规则只依赖变更内容的全序，与到达顺序、节点身份无关。

## 冲突规则（LWW，确定性全序）

同一 key 的并发变更按排序键 `(Seq, Replica, ID)` 裁决，取较大者：

- **并发 set vs set**：排序键较大者获胜，所有副本得出相同结果。
- **并发 delete vs set**：删除不是特权操作，而是带同样排序键的**墓碑**，
  与 set 参与同一全序。删除的排序键更大则删除获胜；反之
  （如删除后因果上更晚的重建，Seq 更大）则更新获胜。
  不存在方向性偏袒，结果稳定且与到达顺序无关。
- 墓碑在压缩时随快照保留（只要仍可能是某 key 的获胜者），
  保证删除语义能传播到所有副本。

## 快照与压缩

- `Snapshot()` 对每个 key 仅保留裁决获胜的变更（含墓碑），
  未知类型变更一律保留，日志重写通过**临时文件 + 原子 rename** 完成。
- 压缩与正常读写互斥但粒度极小；压缩完成后新变更正常追加，
  不会丢失或重复。
- 压缩后若有旧副本以陈旧版本向量再来同步，可能收到重复变更，
  但接收端幂等去重，状态不会分叉。

## 版本兼容策略

- **未知变更类型**：旧副本不改变本地物化状态，但完整保留该变更
  并继续转发；压缩时也不会丢弃。副本升级后即可正确合并。
- **未知数据字段**：反序列化时捕获到 `Change.Extra`，
  重新序列化与持久化时原样保留，跨重启、跨副本不丢失。

## 崩溃恢复

- 日志记录格式为 `长度 + CRC32 + JSON 负载`。启动时扫描到第一条
  截断/校验失败的记录即截断尾部——崩溃时"写了一半"的变更会被丢弃，
  已确认的完整记录绝不丢失。
- 变更先落盘后改内存，重启后从日志完整重建物化状态，
  不存在只应用了一半的状态。
- 快照重写使用原子 rename：压缩中途崩溃，旧日志仍完整可用。
