# offline-sync-engine

本地优先（local-first）的多副本数据同步引擎：支持离线编辑、增量同步、
确定性冲突收敛、快照压缩与崩溃恢复。

## 核心概念

- **Change**：不可变变更记录，由 `(Replica, Seq)` 全局唯一标识，
  携带混合逻辑时钟（HLC）用于冲突排序。
- **VersionVector**：记录本副本已观察到的每个副本的最大序号，
  用于幂等去重与增量同步。
- **WAL**：追加式变更日志，记录格式为 `[4B 长度][4B CRC32][JSON 载荷]`。
- **Snapshot**：某一版本向量时刻的全量状态（含墓碑），用于压缩日志
  与让落后太多的副本追赶。

## 收敛语义

所有副本应用同一变更集后必然收敛到相同状态，与消息到达顺序无关：

1. **幂等**：按 `ChangeID` 去重，重复投递被忽略，不会重复应用。
2. **乱序免疫**：序号不连续的变更先缓存（pending），前驱到达后接续推进
   版本向量；状态合并只依赖 HLC 全序，不依赖到达顺序。
3. **断连恢复**：同步进度完全由版本向量与日志推导，不依赖易损坏的外部
   状态；中途断连后再次执行 `SyncOnce` 即可继续，直至双方版本向量一致。
4. **快照追赶**：若发送方的压缩基线已超过接收方进度（增量日志不够用），
   先按 LWW 逐 key 合并基线快照，再增量补齐，任何进度的副本都能收敛。

## 冲突规则

- 每个 key 采用 **Last-Writer-Wins**：按变更的 HLC 全序
  `(Millis, Counter, Replica)` 比较，大者胜出。
- HLC 的第三分量 `Replica` 仅是同毫秒同计数器时的确定性决胜项，
  保证结果全局一致；除此之外不赋予任何节点优先级。
- **并发删除 vs 并发更新**：删除即写入墓碑，与更新同等对待、同序比较，
  删除不天然优先。HLC 较大的一方胜出（删除赢则 key 消失，更新赢则
  key 保留新值）。墓碑保留在状态与快照中，确保持有旧值的副本能得知
  删除已发生。

## 兼容策略（多版本互通）

- **未知变更类型**：不作用于本地状态，但完整保留在日志与同步流中，
  旧版本副本可无损中转；副本升级后能识别该类型时，回放日志即可合并
  此前保留的数据。压缩不会丢弃未知类型的变更。
- **未知数据字段**：解码时捕获到 `UnknownFields`，编码时原样带回，
  旧版本副本存储、重启、转发均不丢失新版本写入的字段。

## 崩溃恢复

- **先写日志后改内存**：变更先追加 WAL 并 fsync，再作用于内存状态；
  崩溃后由日志回放恢复，不会出现半应用状态。
- **撕裂写截断**：打开日志时顺序扫描，遇长度非法或 CRC 不匹配的记录
  即截断到上一个有效记录末尾，日志始终恢复到一致前缀。
- **原子快照**：快照先写临时文件、fsync、再 rename 覆盖；崩溃残留的
  `.tmp` 文件被忽略，旧快照仍然完整。
- **原子日志压缩**：压缩时新日志同样经临时文件 + rename 替换；
  若在"快照已落盘、日志未截断"之间崩溃，重启后快照与完整日志叠加
  恢复，重复部分按版本向量幂等去重。

## 性能特征

- 加载 = 快照 + 日志尾部回放，不随被压缩的历史增长。
- 增量同步只传输对端版本向量未覆盖的变更。
- 压缩后增量日志有界；快照恢复避免了全量历史回放，
  不阻塞正常读写（快照内容在读锁内固定，文件写在锁外进行）。
